Comment j'ai compté :
Copie de travail : un arbre de travail séparé du dépôt (git worktree, ~/nkmain), au commit f2a8a57 du 14/11/2026 ; le dépôt d'origine n'est pas touché. « Tout le moteur » = les 20 modules du kit Canvas (NKPlatform à NKCanvas, NKAudio, NKMedia, NKNetwork), construits pour Windows avec le même compilateur que le kit : clang 23.1.4 de llvm-mingw, par le toolchain croisé que config/toolchain.jenga prévoit, Jenga 2.10.1, Release, 2 tâches.
Une construction = rm -rf Build ; jenga clean ; puis jenga build --platform Windows --config Release --target X --no-daemon -j 2 pour X = NKCanvas, NKAudio, NKMedia, NKNetwork, toute la sortie dans un fichier (sortie-avant.txt, sortie-apres.txt). Chaque construction recompile les 338 fichiers .cpp une fois chacun (les cibles suivantes trouvent leurs dépendances à jour : aucun fichier n'est compté deux fois).
Compte : clang termine chaque fichier qui a des avertissements par « N warning(s) generated. » ; je fais la somme des N :
  grep -oE "[0-9]+ warnings? generated" sortie-avant.txt | awk '{s+=$1} END {print s}'
Contre-épreuve : le nombre de lignes « [-W...] » de la sortie donne le même total, 1517. Je n'ai pas pris « grep -c warning » : il compte aussi les lignes « 1 warning generated » et les cadres de Jenga, et donne le double.
Premier constat : au niveau d'avertissement du dépôt (aucun -W dans les drapeaux), les deux constructions donnent 0 et 0 : clang ne signale pas une variable inutilisée par défaut, la mienne passait inaperçue. Pour la voir, j'ai refait les deux constructions avec -Wall ajouté aux cxxflags du toolchain, dans la copie seulement : avant 1517, après 1518.
Il a fallu aussi, dans la copie, un en-tête de remplacement pour EventToken.h (en-tête du Windows SDK absent de llvm-mingw, demandé par WebView2.h dans NkWin32WebView.cpp) : sans lui, NKWindow et donc NKCanvas ne se construisent pas en croisé.

Où était le mien :
Kernel/Runtime/NKCanvas/src/NKCanvas/Renderer/Targets/NkRenderTarget.cpp, ligne 18, colonne 8 : « int variableInutilisee = 42; », première ligne du corps de NkRenderTarget::Draw(const NkVertexArray &, const NkRenderStates &). Dans la sortie, c'est le seul fichier de NKCanvas dont le cadre change : « Compiled with warnings: NkRenderTarget.cpp » puis la ligne recopiée dans avertissement.txt et « 1 warning generated. ». NkRenderTarget.cpp n'est compilé que pour une cible : l'avertissement n'apparaît qu'une fois. La variable a été retirée ensuite (fichier remis à l'identique, vérifié par grep : 0 occurrence).
L'écart avant / après est exactement de 1, et il est à moi. Le tas, lui, est très inégal : 1385 des 1517 viennent d'un seul fichier, NKMedia NkVp9Decoder.cpp (-Wmissing-braces, une grande table initialisée sans accolades) ; le reste : -Wunknown-pragmas 45, -Wunused-function 28, -Wunused-variable 16, -Wunused-const-variable 16, et une douzaine d'autres. Sans compte avant / après, un 1518e dans ce tas ne se voit pas.

Ce que coûte la vérification :
Mesuré sur cette machine (2 cœurs) : 3 min 49 s pour la paire de constructions au niveau du dépôt (13 h 40 min 52 s à 13 h 44 min 41 s), 3 min 50 s pour la paire avec -Wall (13 h 44 min 41 s à 13 h 48 min 31 s), soit environ 1 min 55 s par construction complète et 8 minutes en tout, comptage compris. C'est le prix d'une pause, à payer avant chaque envoi qui touche au moteur ; ne compter qu'après une construction incrémentale serait gratuit mais faux, puisque seuls les fichiers recompilés montrent leurs avertissements. Et la vérification n'a de valeur qu'au bon niveau : au niveau par défaut, elle coûte autant et ne voit pas une variable inutilisée.
